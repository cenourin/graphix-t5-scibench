# MEMORY.md

A running log of decisions, findings, and experiment history for the TCC (undergraduate thesis) built on this repo. Where `CLAUDE.md` explains *how the code works*, this file explains *what has been tried, what was found, and why* — read it before re-deriving something that's already been settled here. The canonical, most detailed record of results is always `docs/sciencebenchmark-eval-results.tex` (+ compiled `.pdf`); this file is a higher-level index into that story plus context that doesn't belong in the thesis text itself.

## Repo history

This repo is a personal fork, vendored from `AlibabaResearch/DAMO-ConvAI`'s `graphix/` subdirectory (see `README.md`'s fork notice), created specifically so the TCC would have its own pushable git history under the author's own GitHub account (`origin` = `git@github.com-cenourin:cenourin/graphix-t5-scibench.git`) instead of living inside a throwaway full clone of the Alibaba monorepo. Branches: `main`, `t5-base-scibench-tcc` (the active TCC branch), `llm-model` (a separate remote branch, last synced to an older commit — see any recent commit around branch consolidation for whether/how it was brought up to date).

## Experiment timeline and findings

1. **Zero-shot transfer**: the Spider-trained checkpoint (t5-base + RGAT, 5 epochs on Spider, 41.9%/44.8% EM/exec on Spider dev) evaluated with no retraining on ScienceBenchmark's 299 dev examples: **9.0% EM / 8.87% exec**. A ~33-point drop from in-domain Spider performance — expected, since ScienceBenchmark's schemas (6–25 tables) are much larger/more specific than Spider's (~5.3 tables avg).
2. **Beam search (num_beams=4)**: small, real improvement — **9.34% EM / 9.56% exec** — the best result of the whole project until the Spider-ablation runs (see below) started catching up.
3. **PICARD**: found to be a no-op for the RGAT-aware model path — `rgat_picard.py` bypasses the `model_cls_wrapper` mechanism PICARD's constrained generation relies on. Predictions are byte-identical to plain greedy decoding. Documented as a known integration gap, not fixed (would require merging two class-substitution mechanisms).
4. **Full fine-tuning, oncomx excluded** (`graphix-scibench-finetune`): VRAM (8GB, no gradient checkpointing yet) forced dropping all of `oncomx` from training. Result was *worse* than zero-shot (0% EM / 0.34% exec) — the model overfit to the two domains it saw and generalized badly to `oncomx`, which it never saw at all. This run also exposed two real bugs, both fixed in code and documented in `docs/`:
   - `metric_for_best_model="exact_match"` ties at 0.0 for every checkpoint (generation collapse from no LR warmup) → HF Trainer's strict-greater-than comparison never updates past the first checkpoint → the *least*-trained checkpoint got saved as "best". Fixed everywhere after this by switching to `metric_for_best_model="eval_loss"`.
   - No LR warmup → temporary repetition-loop generation collapse early in training. Fixed with `warmup_ratio=0.1` in every subsequent config.
5. **Few-shot fine-tuning** (300 examples, balanced across domains including a few small `oncomx` examples): also worse than zero-shot (0% EM / 0% exec) — insufficient data plus a checkpoint-spacing mistake meant the actually-most-trained state was never saved.
6. **Gradient checkpointing fix** (`docs/sciencebenchmark-eval-results.tex` §4.2 / `sec:gc-fix`): two bugs fixed — `Model.gradient_checkpointing_enable()` wasn't delegating to the wrapped `pretrain_model`, and `T5Stack.forward()`'s checkpoint closure wasn't re-passing `graph_batch`/`relation_emb` to the checkpointed block. Fixing this let a full fine-tune include **all** of `oncomx` for the first time. Result: eval_loss dropped 2.5x (4.23 → 1.68) but **EM/exec did not improve at all** (still ~0%/0.34%) — a central methodological finding: eval_loss and discrete text-to-SQL metrics can diverge sharply when the model's errors are categorical (wrong table/column name) rather than gradual.
7. **t5-small, no RGAT, ScienceBenchmark ablation** (`plain.py`, `GRAPHIX_MODEL_VARIANT=plain`): the biggest surprise of the project. A *smaller*, RGAT-free model, same data/hyperparameters, **beat every RGAT fine-tuning attempt** (1.38% EM / 1.37% exec vs. the RGAT full-fine-tune's 0%/0.34%) while training 3.4x faster (2h53min vs 9h42min). Not a perfectly controlled ablation (model size and RGAT presence both differ), but directionally clear: within this project's data/hardware budget, RGAT's added complexity didn't pay for itself.
8. **Precision/Recall/F1 (official Spider partial-match evaluator, macro over 10 SQL component types)**: added as a complementary metric. Important quirk to remember — a component absent from *both* prediction and gold scores F1=1 by the evaluator's own definition ("vacuous agreement"), which is why the few-shot run's F1 is a misleading 98.6% despite 0% EM/exec. Don't read macro-F1 as "overall quality" in this project without checking precision/recall alongside it.
9. **Ongoing (as of the most recent session): a 4-run ablation queue** launched to test RGAT-vs-plain on *both* Spider and ScienceBenchmark, for both t5-small and t5-base:
   - `graphix-spider-t5small` (plain, Spider) — early results already **beat the zero-shot RGAT reference** (exec climbing past 14% by epoch 3/5, vs. the reference's 8.87%). If this trend holds, it strengthens finding #7 into "plain T5 competitive with pretrained-RGAT even on Spider itself, RGAT's home turf."
   - `graphix-spider-t5base` (plain, Spider) — queued.
   - `graphix-scibench-t5base-plain` (plain, ScienceBenchmark) — queued, extends #7 to the larger model size.
   - `graphix-scibench-t5small-rgat` (RGAT, untrained from scratch, ScienceBenchmark) — queued, isolates "RGAT vs. no RGAT" at fixed (small) model size, complementing #7's confound.
   - Check `docs/sciencebenchmark-eval-results.tex` for whether these have completed and what they found by the time you're reading this.

## Standing methodological notes (don't re-litigate)

- **Hardware**: everything runs on a single consumer GPU, 8GB VRAM, no tensor cores. This is why `gradient_checkpointing`, `GRAPHIX_MAX_GRAPH_NODES`, and small effective batch sizes appear throughout every ScienceBenchmark config.
- **No genuine held-out test set**: ScienceBenchmark ships only train (seed+synth) and dev; the same dev split used for checkpoint selection is also the one reported as the final number, for every configuration in this project (Spider has the same limitation, so it's methodologically consistent with the base checkpoint's own training — but it's a real caveat for the thesis to state plainly, not hide).
- **4/293 dev examples are always excluded** from EM/exec scoring across every configuration (unparseable gold SQL by `third_party/spider/process_sql.py`, mostly `sdss`'s parenthesized WHERE clauses) — every configuration's "n scored" is consistently 289 (EM) / 287 (exec) for this reason, not because of per-run differences.
- **A hyperparameter grid search was considered and explicitly ruled out** as infeasible on this hardware (each trial = a multi-hour training run on the only GPU available). The hyperparameter choices actually used (LR, warmup, epoch counts, `metric_for_best_model`) are instead justified *empirically, after the fact*, from the training curves already collected — see `docs/sciencebenchmark-eval-results.tex` §4.3 (`sec:hparam-justification`). Don't re-propose a sweep without first checking whether the empirical justification already covers the question at hand.
